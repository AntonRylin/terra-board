# Terra Board server (Docker)

Everything a company needs to run its own Terra Board server on one Linux machine: Supabase's
official self-hosting stack, the Terra Board database schema, sign-in with email codes and
(optionally) SAML company sign-in, HTTPS through [Caddy](https://caddyserver.com/), and the
description file the app reads when someone types your server's address.

People then open Terra Board → Settings → Account → Server → **Change**, type your address
(`terra.acme.eu`), choose **Check** and **Connect**, and sign in. See
[docs/self-hosting.md](../../docs/self-hosting.md) for the app side (links, managed computers).

What the package adds on top of [Supabase's `docker/` folder](https://github.com/supabase/supabase/tree/master/docker)
(downloaded by `setup.mjs` at the tag pinned in `SUPABASE_TAG`):

| File | Does |
| --- | --- |
| `setup.mjs` | Downloads Supabase's files into `supabase/`, writes `.env` with fresh secrets and Terra Board's settings. Safe to run again. |
| `docker-compose.terra.yml` | Override: Caddy in front, email-code templates, SAML, data in `data/`, the `terra-migrate` job, only ports 80/443 open. |
| `Caddyfile`, `caddy-start.sh` | HTTPS, `/.well-known/terra-board.json`, proxy to Supabase's API gateway, the dashboard behind a password. |
| `migrate.sh` | Applies `supabase/migrations` then `ee/supabase/migrations`, each file once, and adds the first admin. |

## Requirements

- A Linux host (x86-64 or arm64) with at least 2 CPUs, 4 GB RAM and 20 GB of disk.
- Docker Engine with Docker Compose v2.24.4 or newer (`docker compose version`).
- `git` and Node.js 18 or newer for `setup.mjs` (no npm packages). No Node? See
  [Setup without Node](#setup-without-node).
- A DNS name for the server (an `A`/`AAAA` record such as `terra.acme.eu` pointing at the host).
- Ports **80** and **443** (TCP, and UDP 443 for HTTP/3) reachable from the internet, or at
  least from wherever Caddy gets its certificate (Let's Encrypt checks port 80 or 443).
- An SMTP account for the sign-in emails (Microsoft 365, Google Workspace, Amazon SES, Postmark,
  Mailgun, your own mail server…).

## Quick start

```bash
git clone https://github.com/AntonRylin/terra-board.git && cd terra-board/ee/server
node setup.mjs --host terra.acme.eu --admin it@acme.eu --name "Acme boards"
nano .env    # set SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASS, SMTP_ADMIN_EMAIL (the sender address)
docker compose up -d
docker compose logs -f terra-migrate    # ends with "terra-migrate: done"
```

Then open `https://terra.acme.eu/.well-known/terra-board.json`: it shows the server's name, its
address and its public key. Connect from the app with the address `terra.acme.eu`.

`docker compose` picks up both compose files by itself: `.env` sets
`COMPOSE_FILE=supabase/docker-compose.yml:docker-compose.terra.yml`. Run every `docker compose`
command from `ee/server`.

The Supabase dashboard (Studio) is at `https://terra.acme.eu/`, user `supabase`, password
`DASHBOARD_PASSWORD` in `.env`. It has full access to the database; put it behind your VPN or
firewall if you can.

`setup.mjs` options: `--host`, `--admin`, `--name`, `--sso` / `--no-sso` (company sign-in),
`--download` (fetch the Supabase files again), `--http` (plain http, only with
`--host localhost`). Running it again keeps every secret and every value you changed in `.env`.

### Try it on your own computer

```bash
node setup.mjs --host localhost --http --admin you@example.com
docker compose up -d
```

In the app, connect to `localhost`. Without SMTP settings no sign-in code is sent; the rest
(`http://localhost/.well-known/terra-board.json`, the dashboard at `http://localhost/`) works.

### Setup without Node

```bash
docker run --rm -it -u "$(id -u):$(id -g)" -v "$PWD/../..:/repo" -w /repo/ee/server \
  node:22-alpine node setup.mjs --host terra.acme.eu --admin it@acme.eu
```

## What `.env` holds

`.env` is the only place with your server's secrets. Keep it private (setup makes it readable
only by you) and back it up: the database cannot be opened without `POSTGRES_PASSWORD`, and
every signed-in session depends on `JWT_SECRET`.

| Setting | Meaning |
| --- | --- |
| `TERRA_HOST`, `TERRA_URL` | The server's DNS name and `https://` address. |
| `TERRA_NAME` | The name people see in the app ("Found Acme boards at terra.acme.eu."). Also written to `public.server_settings`. |
| `TERRA_ADMIN_EMAIL` | First server admin (see below). |
| `SMTP_*` | Mail server for sign-in codes. `SMTP_ADMIN_EMAIL` is the From address, `SMTP_SENDER_NAME` the From name. |
| `SAML_ENABLED`, `SAML_PRIVATE_KEY` | Company sign-in (see below). The key is generated by setup. |
| `ANON_KEY` | The public key. It is in the description file and in every app. |
| `SERVICE_ROLE_KEY` | Full access to everything. **Never** give it to people or put it in the description file or `server.json`. |
| `DISABLE_SIGNUP` | `true` stops new accounts (create them yourself in the dashboard: Authentication → Users → Add user). |
| `TERRA_FILE_SIZE_LIMIT` | Largest file people can upload, in bytes (256 MB). |

Setup turns on email codes (6 digits, valid for an hour, using
[`supabase/templates/email-code.html`](../../supabase/templates/email-code.html) for the "Magic
Link" and "Confirm signup" emails), adds `terraboard://auth/callback` to the allowed redirects,
and turns off anonymous and phone sign-in. `ENABLE_EMAIL_AUTOCONFIRM` must stay `false`: server
admins are recognised by their email address, so every address has to be proven.

After editing `.env`, run `docker compose up -d` again: Compose restarts what changed.

## The first admin

`setup.mjs --admin it@acme.eu` stores `TERRA_ADMIN_EMAIL` in `.env`. Each time `terra-migrate`
runs (every `docker compose up -d`), after the migrations it does

```sql
insert into public.server_admins (email) values ('it@acme.eu') on conflict do nothing;
```

(only if the table exists, so a server without the company migration still starts). The account
does not have to exist yet: when that person signs in with that email address, Terra Board shows
them Settings → **Server admin**. From there they can add more admins, disable people, add the
license key and look at the audit log.

To add an admin by hand:

```bash
docker compose exec db psql -U postgres -c "insert into public.server_admins (email) values ('anna@acme.eu') on conflict do nothing"
```

Removing `TERRA_ADMIN_EMAIL` from `.env` does not remove the admin; do that in the admin panel.

## Company sign-in (SAML SSO)

Terra Board uses Supabase's SAML 2.0 support, so it works with Microsoft Entra ID, Okta, Google
Workspace, Keycloak, OneLogin, JumpCloud and any other SAML identity provider (IdP). People choose
**Continue with company sign-in** and type their work email; the domain picks your IdP.

1. Turn it on and restart:

   ```bash
   node setup.mjs --sso      # sets SAML_ENABLED=true (SAML_PRIVATE_KEY was generated already)
   docker compose up -d
   ```

   `/.well-known/terra-board.json` now says `"sso": true`, and
   `https://terra.acme.eu/auth/v1/settings` shows `"saml_enabled": true`.

2. Create an app in your IdP with these values (replace `terra.acme.eu` with your host):

   | IdP field | Value |
   | --- | --- |
   | Entity ID / Identifier / Audience URI | `https://terra.acme.eu/auth/v1/sso/saml/metadata` |
   | ACS URL / Reply URL / Single sign-on URL | `https://terra.acme.eu/auth/v1/sso/saml/acs` |
   | Name ID format | Email address (`urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress`) |
   | Attribute | the user's email address (see the notes below for its name) |

   Our SP metadata, for IdPs that import it: `https://terra.acme.eu/auth/v1/sso/saml/metadata`.

3. Register the IdP with the server. Run this on the server in `ee/server` (it reads the service
   role key from `.env`, which never leaves the machine):

   ```bash
   SERVICE_ROLE_KEY=$(grep '^SERVICE_ROLE_KEY=' .env | cut -d= -f2-)
   curl -sS -X POST "https://terra.acme.eu/auth/v1/admin/sso/providers" \
     -H "apikey: $SERVICE_ROLE_KEY" \
     -H "Authorization: Bearer $SERVICE_ROLE_KEY" \
     -H "Content-Type: application/json" \
     -d '{
       "type": "saml",
       "metadata_url": "https://login.microsoftonline.com/<tenant-id>/federationmetadata/2007-06/federationmetadata.xml?appid=<app-id>",
       "domains": ["acme.eu"],
       "attribute_mapping": { "keys": { "email": { "name": "http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress" } } }
     }'
   ```

   The answer contains the provider's `id`. If your IdP has no metadata URL, send the metadata
   file instead: replace `"metadata_url": "…"` with `"metadata_xml": "<the XML as one JSON string>"`
   (for example `jq -Rs . idp-metadata.xml` makes that string). Several domains can share one IdP
   (`"domains": ["acme.eu", "acme.de"]`).

   Manage providers with the same headers:

   ```bash
   curl -sS "https://terra.acme.eu/auth/v1/admin/sso/providers" -H "apikey: $SERVICE_ROLE_KEY" -H "Authorization: Bearer $SERVICE_ROLE_KEY"
   curl -sS -X PUT "https://terra.acme.eu/auth/v1/admin/sso/providers/<id>" -H "apikey: $SERVICE_ROLE_KEY" -H "Authorization: Bearer $SERVICE_ROLE_KEY" -H "Content-Type: application/json" -d '{"domains": ["acme.eu"]}'
   curl -sS -X DELETE "https://terra.acme.eu/auth/v1/admin/sso/providers/<id>" -H "apikey: $SERVICE_ROLE_KEY" -H "Authorization: Bearer $SERVICE_ROLE_KEY"
   ```

The server trusts the email address the IdP sends, including for the admin check, so register
only IdPs you control, with only your own domains.

### Microsoft Entra ID

Entra admin center → Enterprise applications → New application → **Create your own
application** → "Integrate any other application you don't find in the gallery (Non-gallery)".
Single sign-on → **SAML**:

- Basic SAML Configuration: Identifier (Entity ID) and Reply URL (ACS URL) from the table above.
- Attributes & Claims: the default `emailaddress` claim (`user.mail`) is the one used in the
  curl example above. Users without a mailbox need `user.userprincipalname` there instead.
- SAML Certificates: copy **App Federation Metadata Url** into `metadata_url`.
- Users and groups: assign the people (or groups) who may sign in.

### Okta

Admin → Applications → **Create App Integration** → SAML 2.0:

- Single sign-on URL: the ACS URL (tick "Use this for Recipient URL and Destination URL").
- Audience URI (SP Entity ID): the Entity ID.
- Name ID format: EmailAddress, Application username: Email.
- Attribute Statements: name `email`, value `user.email`. Use
  `"attribute_mapping": { "keys": { "email": { "name": "email" } } }` in the curl call.
- Sign On tab → **Metadata URL** goes into `metadata_url`. Assign the app to people or groups.

### Google Workspace

Admin console → Apps → Web and mobile apps → Add app → **Add custom SAML app**:

- Google IdP information: **Download metadata** (Google has no metadata URL; send the file as
  `metadata_xml`).
- Service provider details: ACS URL and Entity ID from the table, Name ID format EMAIL, Name ID
  Basic Information → Primary email.
- Attribute mapping: Primary email → `email`, and use
  `"attribute_mapping": { "keys": { "email": { "name": "email" } } }`.
- User access: turn the app **On** for the organisational units that should use Terra Board.

## Updating

```bash
cd terra-board && git pull && cd ee/server
node setup.mjs          # fetches the newly pinned Supabase files if SUPABASE_TAG changed; keeps .env
docker compose pull
docker compose up -d
docker compose logs terra-migrate
```

`terra-migrate` applies only migration files it has not applied before (it keeps a list in
`terra_server.migrations`), so running it again is always safe. To run it on its own:
`docker compose run --rm terra-migrate`. Each file runs in one transaction; if one fails, nothing
from that file is kept and the log says which file.

Before a Supabase update, read `supabase/CHANGELOG.md` of the new version (or Supabase's
[self-hosting changelog](https://github.com/supabase/supabase/blob/master/docker/CHANGELOG.md)).
Postgres major-version upgrades are not automatic; see Supabase's `utils/upgrade-pg17.sh`.
Take a backup first.

## Backups

Everything that matters is in three places:

- `ee/server/data/db`: the Postgres database (accounts, boards, sharing, audit log).
- `ee/server/data/storage`: uploaded files (board pictures, attachments).
- `ee/server/.env`: the secrets. Without it the database cannot be opened.

(Plus the Docker volume `supabase_db-config`, which holds the key of Postgres' encrypted
"vault"; Terra Board does not use the vault, but back it up if you added secrets to it.)

A nightly backup while the server runs:

```bash
cd /path/to/terra-board/ee/server
mkdir -p backup && stamp=$(date +%F)
docker compose exec -T db pg_dump -U supabase_admin -d postgres -Fc > "backup/db-$stamp.dump"
tar czf "backup/storage-$stamp.tgz" -C data storage
cp .env "backup/env-$stamp"
```

The simplest complete backup (a minute of downtime) is a copy of the whole folder while stopped:

```bash
docker compose stop && tar czf "../terra-server-$(date +%F).tgz" .env data && docker compose start
```

To restore it, unpack the archive into `ee/server` of a fresh checkout, run `node setup.mjs`
(it keeps the restored `.env`), then `docker compose up -d`. Copy backups off the machine, and
try a restore once before you need one.
